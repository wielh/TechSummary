# B+ Tree 索引原理與設計考量

在關聯式資料庫（如 MySQL InnoDB、PostgreSQL、SQLite）中，**B+ Tree** 是最廣為使用的索引底層資料結構。理解其設計原理，有助於我們寫出更高效的 SQL 查詢並進行資料庫優化。

---

## 1. B+ Tree 的底層結構

B+ Tree 是一種多路平衡搜尋樹（Multi-way Search Tree），是從 B-Tree 演進而來。其核心結構特點如下：

1. **節點類型分工**：
   * **非葉子節點（Internal/Non-leaf Nodes）**：**只儲存「索引鍵 (Key)」與「子節點指標 (Pointer)」**，不儲存實際的資料行。
   * **葉子節點（Leaf Nodes）**：**儲存所有的「索引鍵」與「實際資料（或主鍵 ID）」**。
2. **葉子節點雙向鏈結**：
   * 所有葉子節點串聯成一個**雙向鏈結串列 (Doubly Linked List)**，且按索引鍵大小順序排列。
3. **平衡性**：
   * 所有葉子節點都位於相同的深度，確保每次查詢的磁碟 I/O 次數相對穩定且可預測。

## 2. B-Tree vs. B+ Tree 深度對比

| 特性 | B-Tree (B 樹) | B+ Tree (B+ 樹) |
| :--- | :--- | :--- |
| **資料儲存位置** | 每個節點（非葉子與葉子）皆儲存 Data | **只有葉子節點**儲存 Data |
| **單頁 Key 容量** | 較少（因為每個節點都要分空間給 Data） | **極多**（頁面能塞入更多索引鍵與指標） |
| **樹的高度 (Height)** | 較高（分支因子 Fan-out 較小） | **極矮**（分支因子極大，一般僅 3~4 層） |
| **範圍查詢效能** | 差（需透過中序走訪跨節點遞迴查找） | **極佳**（沿著葉子節點的雙向鏈結順序讀取） |
| **查詢穩定性** | 不穩定（運氣好在根節點就查到，壞則到葉子） | 極穩定（任何查詢都必須走到葉子節點） |

### 為什麼 B+ Tree 的磁碟 I/O 效率更高？
資料庫是以 **Page (頁)** 為單位進行磁碟與記憶體交換的（MySQL 預設一頁為 16KB）。
* 在 **B-Tree** 中，因為每個節點都塞了整行資料 (Data)，一頁能存的 Key 數量很少。如果資料量大，樹就會變高，查詢時需要讀取更多次磁碟 Page（I/O 次數多）。
* 在 **B+ Tree** 中，非葉子節點只存 Key 與指標。假設一個 Key + 指標佔 16 位元組，一頁就能存下大約 1000 個鍵值（Fan-out = 1000）。
  * 高度為 2 的樹可容納：$1000^2 = 100$ 萬筆資料。
  * 高度為 3 的樹可容納：$1000^3 = 10$ 億筆資料。
  * 這代表**在十億筆數據中找一筆，最多只需 3 次磁碟 I/O**。

## 3. 為什麼不選擇其他資料結構？

### A. 二元搜尋樹 (BST) / 紅黑樹 (R-B Tree)
* **缺點**：它們都是「二元」樹（Fan-out = 2）。當資料量達到百萬級時，樹的高度將會高達約 20 層 ($2^{20} \approx 100$ 萬)。在磁碟儲存結構下，這意味著要進行 20 次隨機磁碟 I/O，效能極差。而 B+ Tree 透過多路平衡，將高度壓縮在 3~4 層。

### B. 哈希表 (Hash Index)
* **缺點**：哈希表雖然能提供 $O(1)$ 的單點查詢速度，但：
  * **不支援範圍查詢**（例如 `WHERE age > 20`），因為雜湊值是無序的。
  * **不支援排序** (`ORDER BY`)。
  * **不支援模糊查詢 / 最左前綴匹配**（如 `LIKE 'ABC%'`）。

## 4. 聚集索引 (Clustered) vs. 非聚集索引 (Secondary)

以 MySQL InnoDB 引擎為例，索引分為兩大類：

### 1. 聚集索引 (Clustered Index / 聚簇索引)
* **定義**：葉子節點直接儲存**完整的資料行**。
* **規則**：一張表**只能有一個**聚集索引（通常是主鍵 Primary Key）。如果沒有設主鍵，MySQL 會自動選一個 Unique 欄位，再沒有則會自動生成隱式 row_id。
* **結構**：
  * Key: 主鍵 ID
  * Value: 整行資料（Name, Age, Email...）

### 2. 非聚集索引 (Secondary Index / 次級/輔助索引)
* **定義**：葉子節點儲存的是**索引鍵值**與對應的**主鍵 ID**。
* **回表 (Lookup)**：當你透過輔助索引查詢時（例如 `WHERE name = 'Alice'`），資料庫會先在 `name` 的 B+ 樹找到對應的 `id`，再拿這個 `id` 去聚集索引的 B+ 樹找到完整的資料行。這個「先查輔助索引，再查主鍵索引」的過程稱為**回表**。
* **覆蓋索引 (Covering Index)**：如果查詢的欄位剛好都在輔助索引樹中（例如 `SELECT id, name FROM users WHERE name = 'Alice'`），資料庫就**不需要回表**，效能會大幅提升。

## 5. 與開發痛點的關聯

B+ Tree 的設計決定了許多 SQL 優化的鐵律：
* **深分頁效能低落的原因**：在 `LIMIT 1000000, 10` 時，因為 B+ Tree 的非葉子節點並不記錄「子樹大小」，所以資料庫無法直接算出第 100 萬筆的物理位置，必須沿著葉子節點鏈結一個一個數過去。如果此時要回表讀取非索引欄位，會造成百萬次無用的磁碟 I/O。詳細優化方案請參考 [mysql 指令應避免事項 - 深分頁問題](file:///e:/code/TechSummary/DB/通用特性/DBSlow.md#L86-L120)。
