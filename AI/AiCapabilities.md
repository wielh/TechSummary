# AI 在軟體開發中的擅長與不擅長領域 (AI Capabilities & Limitations)

## 1. AI 擅長做的事 (AI Excels At)

AI 擅長處理**「規則明確、高度重覆、模式固定、局部上下文」**的任務：

### 樣板程式碼生成 (Boilerplate Code)

- **特點**：產生資料庫 Struct 映射、JSON/XML 結構體、設定檔載入器、基礎 CRUD 介面等。
- **價值**：節省開發者大量的打字與語法排版時間。

### 編寫單元測試與 Mock 資料 (Unit Testing)

- **特點**：根據給定的業務邏輯函數，快速產生測試邊界條件（如 `nil` 檢查、最大值/最小值、空字串）與 Table-driven tests。
- **價值**：開發者最不喜歡寫重複性高的測試，AI 能迅速補齊測試覆蓋率。

### 代碼解釋 (Code Explanation)

- **特點**：閱讀複雜或缺乏文件的遺留代碼（Legacy Code），並為其自動生成註解與文檔說明。

### 程式語言翻譯與轉譯 (Code Translation)

- **特點**：將 Python 腳本轉譯為 Go、JavaScript 轉為 TypeScript，或是將 SQL 查詢轉換為 ORM 代碼（如 GORM、gorm-gen）。

### 正規表達式與資料清洗 (RegEx & Parsing)

- **特點**：撰寫極其繁瑣的正規表達式，或是解析複雜的 Log 日誌格式並將其結構化。

### API 文件的查詢

- **特點**：根據需求，大致確定相關程式位置，可以快速查詢 API 文件的使用方法與參數。

## 2. AI 不擅長（或非常危險）做的事 (AI Struggles With)

AI 在面對**「全域設計、高度抽象、商業邏輯、動態環境、安全隱患」**時表現較弱，極易出錯：

### 全域分散式架構與系統設計 (System Architecture)

- **缺陷**：AI 無法通盤考量網路拓撲、網路延遲（Latency）、硬體資源限制（CPU/Memory/IOPS）、服務間耦合度以及領域模型（DDD）的邊界。
- **後果**：AI 給出的解法往往是局部的。如果讓它主導大型架構設計，容易產生高耦合、不符合實際硬體瓶頸的「空中樓閣」。

### 處理高度客製化與強業務背景的邏輯 (Domain Rules)

- **缺陷**：AI 不知道你們公司的歷史包袱、沒有寫入文件的業務限制、或是前人為了解決特定 Bug 留下的「防禦性程式碼」。
- **後果**：AI 會給出符合業界「標準規範」但完全不符你們公司業務流程的程式碼，並在你不注意時產生嚴重的業務 Bug。

### 長上下文的狀態與連貫性維護 (Long-Context State)

- **缺陷**：在長對話或涉及多個檔案（如 10 個以上）的大重構中，AI 會開始「顧此失彼」，遺忘先前提示詞設定的約束，甚至產出前後相互衝突的邏輯。

### 隱蔽性、併發與低底層 Bug 排查 (Concurrency & Low-level Debugging)

- **缺陷**：
  - **Race Condition (競爭條件)**：多執行緒併發讀寫下的死鎖、原子性遺失。
  - **Memory Leak (記憶體洩漏)**：Go channel 阻塞導致 goroutine 永久殘留、指標未釋放。
  - **系統級問題**：硬體驅動衝突、系統調用 (syscall) 阻塞、GC 垃圾回收長停頓。
- **後果**：AI 無法重現這些動態錯誤，只能給出「重啟試試」、「確認日誌」等泛泛的回答。

### 主動的安全與效能風險評估 (Proactive Risk Assessment)

- **缺陷**：AI 是**被動回應**的。如果你給它一段有 SQL 注入漏洞、記憶體洩漏或缺少 Timeout 設定的代碼，並問它「如何優化排版」，它只會優化排版，**而不會主動警告你其中存在的安全或效能隱患**，除非你明確要求它進行安全性審查。

## 3. 人機協作分工指南 (Human-AI Division of Labor)

為了發揮最大效能，團隊應建立以下分工共識：

| 任務板塊       | 人類開發者 (主導)                                                 | AI 助手 (輔助)                                              |
| :------------- | :---------------------------------------------------------------- | :---------------------------------------------------------- |
| **需求與分析** | **100% 主導**。定義業務需求，釐清邊界條件與商業邏輯限制。         | 腦力激盪、提供業界通用案例或參考架構。                      |
| **架構設計**   | **主導與決策**。設計資料表結構、模組邊界、決定技術選型。          | 根據要求生成基礎 Schema 範本或設計模式腳本。                |
| **程式碼編寫** | 監控、引導與核心邏輯撰寫。                                        | **主力打字員**。生成樣板程式碼、工具函數、註解與 API 宣告。 |
| **單元測試**   | 設計測試場景、確保邊界案例。                                      | **主力生成員**。快速寫出大量測試案例代碼（Table-driven）。  |
| **安全與審查** | **絕對主導**。人工審查（Code Review）每一行代碼，進行漏洞排查。   | 被動式掃描（提示它進行 Vulnerability Check）。              |
| **除錯與調優** | 深入作業系統、網路與 Profiling 工具（如 pprof）進行根本原因分析。 | 根據錯誤訊息（Stack Trace）提供常見可能成因與解決方案草稿。 |
