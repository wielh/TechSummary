# AI 協助編程的工具與注意事項

在現代軟體工程中，利用人工智慧（AI）輔助寫程式已經成為提升生產力的主流方式。正確使用 AI 可以加速功能開發、自動生成測試與文件，但若使用不當，也可能引入嚴重的資安漏洞、智慧財產權糾紛與程式碼品質下降等問題。

---

## 1. 主流 AI 協助編程工具介紹

根據運作模式與應用場景，AI 程式助理主要分為以下兩大類：

### A. IDE 整合與 Agent 代理工具

這類工具直接整合進開發環境中，能讀取專案上下文（Context），甚至能代替人類進行多檔案修改與指令執行：

- **GitHub Copilot**：最經典的程式碼自動補全工具，能根據當前檔案與相鄰檔案即時預測下一行程式碼。
- **Cursor**：基於 VS Code 二次開發的 AI 專用編輯器。其核心優勢是深度整合專案上下文，支援以 `@` 符號引用整個代碼庫（Codebase），並能透過 Composer 同時編輯多個檔案。
- **Cline / Roo Code**：開源的 Agent（智能體）程式助理。它們不僅能寫程式，還能請求權限來**執行終端機指令、建立/讀取檔案、並根據編譯器報錯自動進行修正**。
- **Gemini Code Assist**：Google 推出的開發助理，與 Google Cloud 整合度高，並以大上下文視窗（Large Context Window）見長。

### B. 大語言模型聊天端 (LLM Chat)

適合用於演算法推導、複雜代碼重構設計、架構規劃或學習新技術：

- **Claude 3.5 Sonnet**：目前公認在程式碼邏輯、架構設計與演算法撰寫上最為精準且代碼最乾淨的模型。
- **GPT-4o**：邏輯推理能力強，對複雜程式問題的分析非常全面。
- **Gemini 1.5 Pro**：擁有高達 200 萬 Token 的超大上下文視窗，適合一次將數十個程式檔案或整份系統日誌（Logs）丟給 AI 進行除錯與重構分析。

## 2. 使用 AI 協助編程的五大注意事項（核心安全守則）

### ❌ 注意事項一：資訊安全與敏感資料防護 (Data Privacy)

- **危險性**：將含有資料庫密碼（DSN）、API Key、私鑰（SSH Key）、客戶隱私資料（PII）或公司機密業務邏輯的程式碼貼給公共 AI 模型。這些數據可能會被傳送到雲端並用於未來的模型訓練，導致嚴重的**資料洩漏**。
- **守則**：
  1. 嚴禁將包含真實憑證與金鑰的代碼交給 AI。送出前應進行脫敏處理（以虛擬變數代替）。
  2. 確認所使用工具的隱私政策。例如：使用企業版 GitHub Copilot 或付費版 Cursor 時，應確認已關閉「允許官方使用我的代碼進行訓練」的設定。

### ⚠️ 注意事項二：AI 幻覺問題與人工審查 (Hallucination)

- **危險性**：AI 會寫出看起來「非常專業、語法完全正確」，但**邏輯完全錯誤**的程式碼。有時 AI 還會憑空捏造不存在的依賴庫、API 函數或參數。
- **守則**：
  - **「你是駕駛，AI 是副駕駛」**。不要直接複製貼上。每一行由 AI 生成的程式碼，開發者都必須**讀懂、理解並進行人工代碼審查（Code Review）**後才能併入主分支。

### 🔍 注意事項三：知識庫截止與過期 API (Outdated APIs)

- **危險性**：AI 的訓練資料有截止時間，且容易混淆新舊版本。它可能會使用已廢棄的舊語法（例如在 Go 1.18+ 之後依然使用舊版 Slice 擴容邏輯，或在 Kubernetes 部署中寫入已被廢棄的 apiVersion）。
- **守則**：
  - 對於頻繁更新的框架與套件，務必對照官方最新官方文件。必要時，可將最新文件的 API 宣告複製給 AI，限制它使用最新語法。

### 🛡️ 注意事項四：智慧財產權與開源授權污染 (IP & Licensing)

- **危險性**：AI 在訓練過程中學習了大量開源程式碼。在生成複雜演算法時，AI 可能會直接輸出帶有嚴格傳染性授權（如 GPL、AGPL）的開源程式碼片段。如果將其混入商業閉源專案，可能會面臨法律訴訟與強制開源的風險。
- **守則**：
  - 啟用 IDE 工具的「過濾與公共代碼匹配」（Block suggestions matching public code）功能，防止 AI 直接輸出版權代碼。

### 🧪 注意事項五：缺乏系統架構與耦合考量

- **危險性**：AI 傾向於針對你提出的「局部問題」給出「最快速的局部解法」，這往往會導致程式碼產生大量的重複、硬編碼或不良的模組耦合，破壞原有的專案架構規範。

## 3. 人機協作最佳實踐

1. **規劃整體架構**：可與 AI 討論，但是最終由程序員拍板，並將需求拆分。
2. **Test-Driven AI (測試驅動協作)**：
   - 在讓 AI 寫業務程式碼前，可以先讓它為該需求編寫**單元測試**。利用測試來檢驗 AI 後續生成的業務程式碼是否正確，這是捕捉 AI 程式漏洞最有效的方法，但是需由程序員審查合確認所有 case 都有覆蓋到。
3. **結構化 Prompt (結構化提示詞)**：
   - 撰寫提示詞時，應包含：
     - **Role (角色)**：如「你是一個 Go 語言效能調優專家」。
     - **Context (脈絡)**：提供背景資訊與資料庫結構。
     - **Task (任務)**：精確描述要做什麼。
     - **Constraints (限制)**：如「不使用任何第三方套件」、「必須符合並發安全」。
4. **結合本地編譯與 Linter 驗證**：
   - 代碼生成後，立刻在本地執行靜態分析（如 `golangci-lint`）與單元測試。讓編譯器與工具鏈作為第一道防線，篩選出拼寫、型別或語法層面的低級錯誤。
