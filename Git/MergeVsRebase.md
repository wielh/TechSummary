# Git Merge vs. Rebase 詳細比較

在 Git 中，`merge` 與 `rebase` 是兩種用來整合不同分支變更的主要方式。雖然目的相同，但它們背後的運作機制與對歷史紀錄的影響截然不同。

---

## 1. Git Merge (合併)

`merge` 會將兩個分支的歷史紀錄合併在一起。

### 運作方式

Git 會尋找兩個分支的共同祖先，並執行一次「三方合併 (3-way merge)」，最後產生一個全新的 **Merge Commit**。

### 優點

- **非破壞性**：不會修改既有的提交歷史。
- **完整溯源**：清楚記錄了某個功能是在什麼時候併入主線的。
- **簡單安全**：適用於任何情況，不用擔心影響他人。

### 缺點

- **歷史混亂**：如果頻繁合併，`git log` 會充滿大量的 Merge Commit，歷史線條會變得像「義大利麵」一樣錯綜複雜。

### 適用場景

- **功能開發完成**：準備將 `feature` 分支併入 `main` 或 `develop` 時。
- **團隊共用分支**：合併公共分支的變更。

---

## 2. Git Rebase (重基)

`rebase` 會將當前分支的「基底」移動到目標分支的最新提交上。

### 運作方式

Git 會暫時把當前分支的所有提交拿掉，先將目標分支的新提交接上，再把剛才拿掉的提交一個一個「重新套用」上去。

### 優點

- **歷史線性**：移除不必要的 Merge Commit，讓 `git log` 呈現一條完美的直線，極易閱讀。
- **整理 Commit**：可以配合 `-i` (Interactive) 進行 Squash (合併提交)，讓歷史更簡潔。

### 缺點

- **破壞性 (Rewriting History)**：會改變現有提交的 Hash ID。
- **衝突處理較繁瑣**：如果有 10 個 commit 都有衝突，你可能要解決 10 次衝突（Merge 則只需解決 1 次）。

### 適用場景

- **開發中同步主線**：在 `feature` 分支開發期間，想取得 `main` 的最新變更，使用 `rebase` 保持歷史簡潔。
- **本地整理**：在推送到遠端前，整理自己的 commit 訊息與結構。

---

## 3. 快速比較表

| 特性          | Merge                     | Rebase                     |
| :------------ | :------------------------ | :------------------------- |
| **運作機制**  | 建立一個新的 Merge Commit | 重新定義基底，重新套用提交 |
| **歷史形狀**  | 非線性 (有分支分叉與匯合) | 線性 (一條直線)            |
| **Commit ID** | 保留原始 ID               | 產生新的 ID                |
| **衝突處理**  | 一次性解決所有衝突        | 逐個 Commit 解決衝突       |
| **適用時機**  | 最終合併、公共分支        | 個人開發、整理歷史         |

---

## 4. 黃金法則 (The Golden Rule of Rebase)

> **絕對不要在公共分支 (Public Branch) 上執行 Rebase！**

如果你對已經推送到遠端、且他人也在使用的分支（如 `main`）執行 Rebase，這會導致他人的歷史與遠端不一致，造成嚴重的同步衝突。

---

## 5. 實戰建議：該選哪一個？

### 推薦流程

1. **開發期間 (Local Feature Branch)**：
   使用 `git rebase main` 來同步主幹變更，保持開發線條整齊。
2. **準備合併 (Before Pull Request)**：
   使用 `git rebase -i` 進行清理，將瑣碎的 commit (如 "fix typo") 合併掉。
3. **正式併入 (Final Integration)**：
   使用 `git merge feature-branch` 將功能併入主幹，留下明確的合併紀錄。

這種做法結合了兩者的優點：**開發過程乾淨線性，合併過程清晰可見。**
