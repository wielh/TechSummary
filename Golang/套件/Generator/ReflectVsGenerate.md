# Reflect vs. Generate: 該選擇哪一種？

在 Go 語言中，當我們需要處理高度動態的邏輯或減少重複代碼時，通常有兩種主要手段：**反射 (Reflection)** 與 **代碼生成 (Code Generation)**。

---

## 1. 反射 (Reflect)

反射是在「執行期 (Runtime)」檢查、修改程式碼結構的能力。

### 優點

- **靈活性極高**：可以在不知道具體類型的情況下處理資料（如 `json.Marshal`）。
- **無需額外步驟**：不需要手動執行指令，代碼寫完直接執行。

### 缺點

- **效能開銷**：反射需要大量的元數據查找與類型檢查，通常比直接呼叫慢 10-100 倍。
- **類型不安全**：許多錯誤只能在執行期發現（Panic），而非編譯期。
- **代碼難讀**：反射的程式碼通常充滿了 `reflect.Value`, `reflect.Type`，邏輯較晦澀。

---

## 2. 代碼生成 (Generate)

代碼生成是在「編譯期 (Compile-time)」預先產出強類型的 Go 代碼。

### 優點

- **效能優異**：生成的代碼就是普通的 Go 代碼，沒有任何反射開銷。
- **類型安全**：所有的錯誤都能在編譯期被攔截，並享有 IDE 的自動補完。
- **語意清晰**：生成的代碼直觀易懂，方便追蹤 Bug。

### 缺點

- **增加開發步驟**：每次修改元資料（如 Protobuf 或 DB Schema）後，必須手動執行 `go generate`。
- **檔案冗餘**：專案中會多出許多 `.gen.go` 檔案。

---

## 3. 核心對比

| 特性         | 反射 (Reflect)            | 代碼生成 (Generate)             |
| :----------- | :------------------------ | :------------------------------ |
| **發生時間** | 執行期 (Runtime)          | 編譯期 (Compile-time)           |
| **效能**     | 較慢 (需要運算類型資訊)   | 極快 (與原生代碼無異)           |
| **類型檢查** | 執行期發現錯誤 (易 Panic) | 編譯期發現錯誤 (安全)           |
| **維護成本** | 較低 (代碼量少，但複雜)   | 較高 (需維護生成器與生成的檔案) |
| **開發體驗** | IDE 提示較弱              | IDE 提示極強 (強型別)           |

---

## 4. Go 推薦哪一種？

Go 官方與社群普遍更推薦使用「代碼生成 (Code Generation)」。

1. **符合 Go 的設計哲學**：Go 傾向於「顯式勝過隱式 (Explicit is better than implicit)」以及「編譯期安全」。
2. **效能考量**：Go 常被用於高效能後端服務，反射帶來的額外負擔在處理大量請求時會變得非常明顯。
3. **工具鏈支援**：Go 內建了 `go generate` 指令，並提供了 `go/ast`, `go/parser` 等強大的標準庫來支援開發者撰寫生成工具。

---

## 5. 決策建議

### 優先選擇「反射」的情況

- 撰寫通用的函式庫（如 `encoding/json`），且無法預知使用者會傳入什麼類型。
- 邏輯非常簡單，反射帶來的效能損失可忽略不計，但能大幅減少代碼量。

### 優先選擇「代碼生成」的情況

- **效能敏感** 的場景（如：高效能序列化、資料庫查詢）。
- **結構固定** 但重複性高（如：Protobuf、Mock Object、GORM Models）。
- 想要在開發過程中獲得 **強類型保護** 與 IDE 自動補完。

### 總結

「能用代碼生成解決的，就不要用反射。」 這是 Go 開發中的一條準則。雖然代碼生成多了一個步驟，但它帶來的安全性與效能優勢在專案長期維護中是非常巨大的。
