# Golang Mocking 策略對比

在 Go 的單元測試中，替換外部依賴主要有兩大流派：基於介面設計的 **Interface Mock** 與基於運行時替換的 **Monkey Patch**。

---

## 1. 核心對比表

| 特性         | Interface Mock (推薦)              | Monkey Patch (特殊手段)                |
| :----------- | :--------------------------------- | :------------------------------------- |
| **代表工具** | `mockgen`, `testify/mock`          | `bou.ke/monkey`, `gomonkey`            |
| **運作原理** | 實作 Interface，利用 **多型** 替換 | 修改 **函式指標 (Function Pointer)**   |
| **侵入性**   | **高**。必須將依賴寫成 Interface   | **低**。不需要改動任何原始碼           |
| **類型安全** | **強**。編譯期即可發現錯誤         | **弱**。繞過編譯檢查，出錯會導致 Panic |
| **執行要求** | 無特殊要求                         | **必須禁用內聯** (`-gcflags="all=-l"`) |
| **架構影響** | 促進 **解耦 (Decoupling)**         | 可能掩蓋糟糕的耦合設計                 |
| **維護成本** | 較低。結構清晰，易於理解           | 較高。容易因編譯器優化或底層異動而失效 |

---

## 2. 深入分析

### Interface Mocking (正規軍)

這是 Go 社群最推崇的方式。它要求你針對「行為」定義介面，並透過 **依賴注入 (Dependency Injection)** 將 Mock 實例傳入。

- **優點**：
  - 強迫你思考組件之間的邊界。
  - 測試執行速度快且穩定。
  - 符合物件導向的 SOLID 原則。
- **缺點**：
  - 需要寫較多的 Boilerplate code (雖然可用 `mockgen` 生成)。
  - 對於已經寫死 (Hardcoded) 的代碼，需要進行重構才能測試。

### Monkey Patching (特種部隊)

這是一種「暴力」但有效的手段，它在運行時直接跳到你指定的 Mock 函式。

- **優點**：
  - 能夠 Mock 那些「不可 Mock」的東西：全域函式、靜態方法、標準庫 (`time.Now`, `os.Exit`)。
  - 適合用於修復難以重構的遺留系統 (Legacy Code)。
- **缺點**：
  - **執行期風險**：直接操作記憶體，不支援並行測試 (Not Thread-safe)。
  - **環境依賴**：依賴特定的 CPU 架構與編譯器行為。
  - **效能優化衝突**：與編譯器的內聯優化衝突。

---

## 3. 選用建議

### 什麼時候用 Interface Mock？

- **絕大多數情況**。
- 當你在設計內部的 Service、Repository、Controller 時。
- 當你希望代碼結構清晰、易於長期維護時。

### 什麼時候用 Monkey Patch？

- **外部不可控因素**：例如 Mock `time.Now()` 或是 `http.Get` (如果你沒封裝它)。
- **維護舊程式**：面臨無法重構但必須寫測試的 Legacy Code。
- **快速原型開發**：臨時需要遮斷某個深層依賴進行驗證。

> **金句良言**：
> 如果你發現自己需要大量使用 Monkey Patch，通常代表你的系統 **架構設計出了問題**（耦合太重）。應優先考慮引入 Interface。
