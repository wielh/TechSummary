# Redis 核心概念與最佳實踐

Redis（Remote Dictionary Server）是一款開源、基於記憶體的高效能鍵值對（Key-Value）非關聯式資料庫。

---

## 1. 核心基本特性

* **單線程模型 (Single-Threading)**：
  * Redis 的網路 I/O 與指令執行主要在一個主線程中完成。這避免了多線程上下文切換（Context Switch）的開銷與鎖競爭問題，也是 Redis 能維持極速讀寫的主因。
  * *註：Redis 6.0+ 在網路 I/O 階段引入了多線程輔助，但指令執行依然是單線程的；另外，大檔案關閉、非同步刪除（如 `UNLINK`）也是在背景線程執行的。*
* **記憶體儲存 (In-Memory)**：
  * 資料全部存放在記憶體中，讀寫操作皆為記憶體速度，讀寫效能可達每秒 10 萬次以上 (100k+ QPS)。
* **持久化機制 (Persistence)**：
  * 雖然是記憶體資料庫，但提供兩種持久化方式防止資料遺失：
    * **RDB (Redis Database File)**：定期的資料快照。
    * **AOF (Append Only File)**：將每個寫指令追加記錄到檔案中。
* **高可用與擴展性**：
  * **主從複製 (Replication)**：實現資料備份與讀寫分離。
  * **哨兵模式 (Sentinel)**：自動化監控主節點，並在故障時進行自動容錯切換 (Failover)。
  * **分片群集 (Cluster)**：分散式架構，支援橫向擴展與自動資料分片。

---

## 2. 交易 (Transaction) 與 ACID 保證

Redis 的交易透過 `MULTI`、`EXEC`、`DISCARD` 和 `WATCH` 指令實現：

* **原子性 (Atomicity)**：
  * Redis 交易會將多個指令排入佇列後**一次性順序執行**。執行期間不會被其他客戶端的指令插隊。
  * **⚠️ 注意：Redis 交易不支援回滾 (Rollback)**。如果事務中某個指令在運行時出錯，其他正確的指令依然會被執行完畢。
* **一致性 (Consistency)**：
  * 配合 `WATCH` 指令（樂觀鎖機制）可以監控某些鍵。如果在交易執行前這些鍵被其他客戶端修改，整個交易會被取消執行，確保一致性。
* **隔離性 (Isolation)**：
  * 由於單線程模型，交易在執行時是序列化的，其他客戶端無法看到交易中間的過渡狀態，天然具備串行化（Serializable）的隔離效果。
* **持久性 (Durability)**：
  * 預設無持久性保證。持久性完全取決於 AOF 配置的 `appendfsync` 策略（如 `always`、`everysec`）。

## 3. 核心資料型態與場景

| 資料型態 | 特點 | 常見使用場景 |
| :--- | :--- | :--- |
| **String (字串)** | 最基礎的鍵值對，最大 512MB。 | 一般快取、計數器（`INCR`）、分佈式鎖。 |
| **List (列表)** | 雙向鏈結串列，保證插入順序。 | 簡單消息佇列（`LPUSH` + `RPOP`）、最新消息排行榜。 |
| **Hash (哈希)** | 鍵值對集合，適合儲存物件。 | 儲存用戶個人資料、購物車商品清單。 |
| **Set (無序集合)** | 無序且唯一的元素集合，支援交集/聯集。 | 共同好友、標籤系統、抽獎活動。 |
| **ZSet (有序集合)** | 每個元素關聯一個 Score 分數，自動排序。 | 積分排行榜、帶權重的任務佇列。 |
| **Bitmap (點陣圖)** | 基於 String，以 Bit 位元（0/1）儲存。 | 用戶簽到記錄、二值狀態統計（如是否在線）。 |

## 4. 記憶體管理與過期淘汰策略

當 Redis 記憶體空間不足，或是 Key 到達過期時間時，Redis 的處理機制如下：

### A. 過期刪除策略
1. **惰性刪除 (Lazy Expiration)**：當用戶存取某個 Key 時，Redis 會先檢查它是否過期，若過期則予以刪除。這對 CPU 友善，但可能造成記憶體浪費。
2. **定期隨機刪除 (Periodic Active Expiration)**：Redis 每秒進行 10 次掃描，隨機抽取一部分設有過期時間的 Key，若過期則刪除。

### B. 記憶體淘汰機制 (Memory Eviction)
當記憶體使用量達到最大限制 (`maxmemory`) 時，會觸發淘汰策略：
* **`noeviction`**（預設）：不淘汰任何資料。寫入指令直接報錯，僅允許讀取與刪除。
* **`allkeys-lru`**：從所有 Key 中，使用 LRU（最近最少使用）演算法淘汰資料。**最常用的快取配置**。
* **`volatile-lru`**：僅從「設有過期時間」的 Key 中，使用 LRU 淘汰資料。
* **`allkeys-lfu`**：使用 LFU（最不經常使用，頻率最低）演算法淘汰所有 Key。
* **`volatile-lfu`**：僅對設有過期時間的 Key 使用 LFU 淘汰。
* **`volatile-ttl`**：優先淘汰剩餘存活時間 (TTL) 最短的 Key。
* **`allkeys-random` / `volatile-random`**：隨機淘汰 Key。

## 5. 快取三大痛點與實戰解決方案

在生產環境中，快取層的設計必須面對以下三個嚴重危害資料庫的併發問題：

### 1. 快取穿透 (Cache Penetration)
* **成因**：使用者頻繁請求**快取和資料庫中都不存在**的資料（例如惡意掃描不存在的 `id = -999`）。因為快取查不到，請求會全部打到後端資料庫，導致資料庫崩潰。
* **解決方案**：
  1. **快取空值 (Cache Null)**：當 DB 返回空時，依然將此空值回寫到快取中，並設定一個較短的過期時間（例如 1~5 分鐘）。
  2. **布隆過濾器 (Bloom Filter)**：在快取前加設布隆過濾器。布隆過濾器能以極小的空間判斷一個元素「是否絕對不存在」，若不存在則直接攔截請求。

### 2. 快取擊穿 (Cache Breakdown)
* **成因**：一個**熱點 Key**（如某熱賣商品的詳情）在某一瞬間過期失效，此時大量對該 Key 的併發請求瞬間打入，導致資料庫負載過高。
* **解決方案**：
  1. **互斥鎖 (Mutex)**：在快取失效時，只允許一個線程獲取鎖去查詢 DB 並回寫快取，其他線程等待並重試（適合強一致性要求）。
  2. **Go 語言的 `SingleFlight` 機制**：在 Go API 開發中，使用 `golang.org/x/sync/singleflight` 可以將多個併發的相同 Key 查詢合併為同一次 DB 查詢，只讓一個 Goroutine 去查，其餘共享該結果，極大降低 DB 壓力。
  3. **熱點資料永不過期**：由背景腳本定時更新該熱點 Key，或動態延長過期時間。

### 3. 快取雪崩 (Cache Avalanche)
* **成因**：**大量 Key 在同一時間點集體過期**，或 **Redis 伺服器宕機**，導致大量請求瞬間全部湧入資料庫，造成整個系統崩潰。
* **解決方案**：
  1. **隨機過期時間 (Randomized TTL)**：在設定過期時間時，加上一個隨機偏移行（例如 `Base TTL (30m) + Random (1~5m)`），防止 Key 同時過期。
  2. **雙層快取/多級快取**：本地快取（記憶體）+ 遠端快取（Redis）雙重防護。
  3. **Redis 高可用群集**：使用 Redis Cluster 或 Sentinel 避免單點故障。
